## 2. 最终目标与明确边界

### 2.1 产品北极星

让组织者能够自助创建和运营活动，让参与者能够安全完成浏览、报名、支付、获取入场权益、核销和交流，并让平台能够对权限、资金、库存、履约和故障进行完整审计。

### 2.2 三个关键里程碑

| 里程碑 | 定义 | 必须完成 |
|---|---|---|
| **M1 可用** | 普通用户和运营人员可以在移动端稳定完成免费活动全流程，无需开发者改库或手工兜底 | G0 至 G4 |
| **M2 可上线** | 系统可以在生产环境安全部署、监控、备份、恢复和回滚，多个组织者之间数据隔离 | G5 至 G6 |
| **M3 可商业化** | 系统不仅能收款，还能正确处理订单、支付、退款、核销、对账、审计和持续经营指标 | G7 至 G8 |

### 2.3 非目标

- 商业闭环验证前不拆微服务。
- 不为了“架构先进”一次性替换 Go 标准库、Vue 或所有数据访问代码。
- 不在缺少容量、SLO 或成本证据时提前引入消息队列、搜索集群、Kubernetes。
- 不把 Registration 直接扩展成订单、支付和核销的万能表。
- 不以测试数量、总覆盖率或主观评分单独代表质量。

## 3. 当前基线

### 3.1 已有优势

- 已完成门店、活动、报名、门票、讨论、用户认证和管理接口，共 25 个 API。
- 后端采用清晰的 handler、model、store 分层，适合继续演进为模块化单体。
- SQLite 已覆盖基础事务、库存扣减、取消报名退库存和活动级联清理。
- Go 侧已有 202 个顶层测试，当前验证中 go test、race、vet、gofmt 均通过。
- Vue 3、TypeScript、Element Plus 前端能够完成生产构建。
- README、完整任务记录和历史测试报告提供了较完整的演进背景。

### 3.2 阻止上线的现状

| 风险 | 当前表现 | 目标阶段 |
|---|---|---|
| 管理认证 fail-open | ADMIN_TOKEN 为空时管理接口放行 | G1 |
| 用户身份可冒用 | 报名、取消、讨论仍可回退到请求体联系方式 | G1、G2 |
| 隐私数据公开 | 报名列表公开返回姓名和联系方式 | G1 |
| 前后端契约错误 | 帖子详情响应结构与前端类型不一致 | G1 |
| 资源归属缺失 | 嵌套路由没有验证 ticket/post 是否属于 URL 中的 event | G1 |
| 数据校验不一致 | 创建接口有校验，更新接口可写入非法值 | G1 |
| 数据迁移不可追溯 | ALTER 错误被忽略，没有 schema 版本和迁移验证 | G2 |
| 身份模型割裂 | User 与 Registration、Post、Reply 没有可靠 ID 关联 | G2 |
| 前端质量门禁缺失 | 没有 lint、unit/component、E2E 测试 | G0、G4 |
| 运维基线不足 | 无 CI/CD、告警、备份恢复演练、发布回滚证据 | G0、G6 |
| 管理能力不完整 | 门店和门票虽有 API，但缺少完整后台闭环 | G4、G5 |
| 交易域缺失 | 价格和库存不等于订单、支付、退款、结算 | G7 |

### 3.3 基线可信度规则

- v5.1 历史报告中的覆盖率和评分仅作为历史参考。
- G0 必须在干净环境和固定工具链上重新生成带完整 Commit SHA 的基线报告。
- 当前 test_reports/ 被 .gitignore 忽略，里面的文件不能作为新克隆可获得的发布证据。
- 原始测试产物继续放在 test_reports/ 或 CI Artifact；可提交的摘要放在 docs/releases/。

## 5.3 G2 用户身份与数据模型 v2

**目标**：User ID 成为报名、取消、讨论和后续核销的唯一可信身份源，联系方式只作为资料，不再作为授权凭据。

### 范围

- [x] **G2-R01** 引入版本化数据库迁移和 schema_migrations。
- [x] **G2-R02** registrations 增加 nullable user_id，并建立仅对非空 user_id 生效的新唯一约束。
- [x] **G2-R03** posts、replies 增加作者 user_id，授权逻辑统一使用 ID。
- [x] **G2-R04** 新增 /api/me/registrations 和单活动报名状态接口。
- [x] **G2-R05** 登录后报名免填姓名和联系方式；取消、发帖、回复必须使用 JWT 身份。
- [x] **G2-R06** 完成精确联系方式回填、legacy 标记和管理员人工处理清单。
- [x] **G2-R07** 可靠启用 SQLite 外键，并通过 [ADR-001](adr/001-sqlite-foreign-key-and-deletion-semantics.md) 固化门店、活动、门票和用户删除语义。
- [x] **G2-R08** 增加真实文件数据库的空库、旧库、重复执行、失败返回和备份恢复测试。
- [x] **G2-R09** 增加并发容量、库存扣减和重复取消退库存测试。

### 数据迁移顺序

1. Expand：新增 nullable 列和新索引，不删除旧列。
2. Backfill：按可验证规则匹配用户，无法匹配的数据标记 legacy。
3. Dual path：应用暂时兼容新旧数据读取，新增数据只写可信 user_id。
4. Verify：核对总数、重复记录、孤儿记录、库存和报名关系。
5. Switch：授权与主要查询切换到 user_id。
6. Contract：至少跨一个兼容版本后再考虑移除旧授权路径。

### 完成门槛

- [x] 用户只能取消自己的报名、以自己的身份讨论。
- [x] 历史数据迁移结果有总量、成功、失败和人工处理清单。
- [x] 迁移在空库、v5.1 旧库、重复执行三种场景通过。
- [x] 并发报名不超过容量，门票库存不为负，取消不丢库存。
- [x] 迁移前备份和恢复演练通过。

## 5.4 G3 受控架构重构与契约稳定

**目标**：提高可测试性和变更隔离能力，但不进行大爆炸式分层重写。

### 目标结构

    HTTP / Router
        -> Handler + HTTP DTO
        -> Application Service
        -> Domain Rules
        -> Repository / Store
        -> SQLite 或后续 PostgreSQL

    Application Service
        -> Payment / Notification / Object Storage 等外部适配器

### 范围

- [ ] **G3-R01** Config 在启动时一次性加载、校验并注入，不在请求中重复读取环境变量。
- [ ] **G3-R02** NewStore 返回 error，库层不再 log.Fatal。
- [ ] **G3-R03** 只为报名、取消、核销、订单等跨实体事务引入 service。
- [ ] **G3-R04** HTTP DTO 与数据库实体逐步分离，固定 API 响应契约。
- [ ] **G3-R05** repository 接口由调用方和具体业务需求定义，不提前抽象全部 CRUD。
- [ ] **G3-R06** 注入 clock、token signer、ID generator 等难以测试的依赖。
- [ ] **G3-R07** 建立 OpenAPI 契约和契约测试；新 API 进入 /api/v1。
- [ ] **G3-R08** 建立稳定业务错误码，HTTP 状态码与业务错误分离。

### 受控重构规则

1. 先补表征测试，再移动代码。
2. 一个 PR 只改变代码结构、数据库、API、业务规则中的一个轴。
3. 不把功能开发和大范围重命名混在同一 PR。
4. 每个高风险数据迁移单独提交并提供前向修复和恢复方案。
5. 旧 API 至少兼容一个发布周期，除非存在必须立即关闭的安全漏洞。
6. 新旧实现可以短期并存，通过 Feature Flag 或路由切换灰度。
7. service 只承载业务不变量和事务，不把简单查询机械搬迁。
8. 商业闭环验证前保持模块化单体。

### 完成门槛

- [ ] 重构前后 API 契约和核心用户旅程行为等价。
- [ ] handler 不再承载跨实体事务规则。
- [ ] OpenAPI 契约测试通过。
- [ ] 新增关键领域逻辑具备完整的正常、拒绝、边界和故障回归场景。
- [ ] 每次重构都有独立回滚方式，不依赖手工改库。

## 5.7 G6 生产上线准备

**目标**：系统能够安全部署、观测、备份、恢复和回滚，达到 M2“可上线”。

### 部署与供应链

- [ ] **G6-R01** staging、production 环境隔离，配置和密钥由安全存储管理。
- [ ] **G6-R02** CI/CD 生成不可变制品，记录版本、Commit SHA、依赖和构建环境。
- [ ] **G6-R03** Docker 非 root 运行，固定基础镜像版本，提供 Healthcheck 和 smoke test。
- [ ] **G6-R04** HTTPS、域名、CORS、限流、安全头、依赖和 Secret 扫描。
- [ ] **G6-R05** 数据库迁移先于应用灰度，并保持 N/N-1 应用兼容。

### 可观测性与运维

- [ ] **G6-R06** request_id、结构化日志、指标、错误追踪和告警。
- [ ] **G6-R07** liveness 与 readiness 分离，依赖异常时返回可操作状态。
- [ ] **G6-R08** 部署、迁移、备份恢复、回滚、支付关闭、故障响应 Runbook。
- [ ] **G6-R09** 自动备份、保留策略、恢复验证和定期演练。
- [ ] **G6-R10** 审计、隐私请求、账号注销、数据导出/删除和留存流程。

### 数据库决策闸门

真实支付前默认迁移至托管 PostgreSQL。若选择继续使用 SQLite，必须通过 ADR 证明：

- 单实例满足目标可用性和维护窗口。
- 写并发、备份恢复、锁等待和故障恢复满足 SLO。
- 不需要多实例、高可用或托管数据库能力。

| 关键 API 5xx | < 1% | < 0.1% |

| RTO | ≤ 4 小时 | ≤ 60 分钟 |

## 5.8 G7 订单支付与真实 Beta

**目标**：先建立正确的交易领域，再接入一个支付渠道，完成真实小流量收费闭环。

### 领域模型约束

| 模型 | 职责 |
|---|---|
| Order | 交易合同、买方、金额、状态和业务快照 |
| OrderItem | 购买的票种、数量、单价和规则快照 |
| Payment | 支付渠道交易、回调、支付状态和幂等 |
| Refund | 退款请求、渠道结果、金额和审批状态 |
| Registration | 参与者与活动的实名参与关系 |
| Admission | 一张可转交、可失效、可核销的入场权益 |
| Checkin | 不可变的核销事件与审计记录 |
| InventoryReservation | 下单时的库存预占和超时释放 |

Order、Registration、Admission、Checkin 不合表。免费票也可以走 0 元订单，但只有订单成功后才生成参与关系和入场权益。

### 范围

- [ ] **G7-R01** 金额统一使用整数最小货币单位，例如 price_cents，禁止用 float64 结算。
- [ ] **G7-R02** 建立订单状态机：pending、paid、closed、refunding、refunded。
- [ ] **G7-R03** 库存预占、超时释放、支付成功扣减和退款后的权益处理。
- [ ] **G7-R04** 支付适配器接口，首期只接一个官方渠道和沙箱。
- [ ] **G7-R05** 幂等键、回调验签、防重放、重复/乱序回调处理。
- [ ] **G7-R06** webhook_events 原始记录、Outbox、失败重试和可重放能力。
- [ ] **G7-R07** 全额/部分退款、已核销退款审批和 Admission 失效规则。
- [ ] **G7-R08** 日终订单、支付、退款、库存、报名和凭证对账。
- [ ] **G7-R09** 主办方结算报表、平台服务费和支付渠道成本记录。

### 资金与合规原则

- 优先采用主办方直连商户或支付机构官方服务商/分账模式。
- 不采用平台归集资金后人工打款的方式。
- 商户资质、发票税务、退款责任和支付合规需由实际支付机构及专业顾问确认。
- 生产真实支付必须可一键停止新下单，同时保留订单查询和退款处理。

### 测试重点

- 支付成功、失败、超时、重复回调、乱序回调和回调重放。
- 全额退款、部分退款、重复退款、渠道超时和人工审核。
- 100 并发抢同一库存，不超卖、不重复出票。
- 故障注入后无悬挂库存、重复扣款、重复退款或重复 Admission。
- 沙箱和真实小额订单的日终对账差额必须为 0。

### 完成门槛

- [ ] 至少 2 个独立组织者、3 场真实活动、50 笔真实小额订单。
- [ ] 账、单、票、库存和退款差额为 0。
- [ ] 越权、重复扣款、重复退款和资金事故为 0。
- [ ] 退款和投诉全部在承诺 SLA 内闭环。
- [ ] 未达标时不得扩大支付流量。

## 6. 两周迭代节奏

### 6.1 标准节奏

| 时间 | 重点 |
|---|---|
| Day 0–1 | DoR、范围冻结、Goal/Requirement ID、验收条件、风险、数据迁移和测试计划 |
| Day 2–6 | 小 PR 实现；代码、测试、文档同 PR；快速门禁持续通过 |
| Day 7–8 | 集成、契约、E2E、迁移、并发和授权测试 |
| Day 9 | 功能冻结；staging、备份恢复、回滚和 smoke 验证 |
| Day 10 | 更新 goal 状态、README、CHANGELOG、发布资料，完成 Go/No-Go 和复盘 |

### 6.2 容量建议

- G0 至 G3：30% 功能、50% 质量与重构、20% 测试文档。
- G4 至 G6：60% 产品、25% 工程质量、15% 文档运维。
- G7 交易阶段：40% 业务、40% 正确性与故障测试、20% 对账与运维。
- 每次迭代只交付一个纵向业务闭环和一个质量主题。
- WIP 不超过 2；重构使用独立小 PR。

### 6.3 Git 与版本规则

- 稳定分支：main。
- 功能分支：feature/*。
- 修复分支：fix/*。
- 提交格式：feat、fix、docs、refactor、test、chore 加简明描述。
- patch：向后兼容修复。
- minor：向后兼容功能。
- major：破坏 API、数据或客户端兼容性。
- Git Tag 必须指向实际完成全量验证的 Commit。

## 8. Definition of Ready 与 Definition of Done

### 8.1 Definition of Ready

进入开发前必须满足：

- 有明确用户价值、范围和非目标。
- 有稳定 Requirement ID 和可验证验收条件。
- 已标注风险等级、依赖和 Owner。
- API、数据、权限和兼容性影响已说明。
- 数据迁移、备份和回滚方案已说明。
- 自动化与人工测试设计已进入追溯矩阵。
- README、OpenAPI、ADR、Runbook、Release 文档影响已识别。

### 8.2 任务级 Definition of Done

- Requirement 和验收条件全部满足。
- 行为变化有自动化测试，Bug 有回归测试。
- gofmt 无差异。
- go test -count=1 ./... 通过。
- go test -race -count=1 ./... 通过。
- go vet ./... 通过。
- 前端至少 npm ci 与 npm run build 通过；测试体系建立后必须 lint、unit 通过。
- API、配置、schema、运行方式变化在同一 PR 更新对应文档。
- 无新增 Secret、PII 泄露或未授权访问。
- 数据迁移完成前向验证，并有备份、恢复或 forward-fix 策略。
- 无未关闭 P0/P1；延期 P2 必须记录 Owner、期限和风险接受。

### 8.3 阶段与发布级 Definition of Done

- 所有阶段验收条件都有证据，高风险项在矩阵中无空白。
- 干净环境和同一 Commit 上完成全量门禁。
- 关键身份、授权、库存和资金不变量场景全部覆盖。
- M1 必须完成核心用户旅程 E2E。
- M2 必须完成真实迁移、Docker/staging、备份恢复、并发、安全、性能和回滚验证。
- M3 必须完成支付幂等、回调重放、退款、对账、审计、隐私和灾备验证。
- 生成 release-notes、test-report、known-issues、migration-rollback。
- Tag 指向已验证 Commit，部署后 smoke 和观察窗口通过。
